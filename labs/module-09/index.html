Key Concepts

Program and product roles — non-code or semi-technical users — author agent-assisted workflows in Atlassian Rovo Studio. This sits alongside the Copilot and MCP engineering workflows, not on top of them: it is where business intent becomes agent execution.

A workflow is a chain the business user assembles on a canvas — and every published workflow is versioned and has an owner.

Trigger
An event or automation rule — a new issue, a schedule, a status change
→
Actions & connectors

→
Approval & checkpoints
Approval flows and human-in-the-loop checkpoints on consequential steps
→
Publish
Versioned, owned, and handed to technical owners for implementation

A studio agent is only useful when it is grounded on real project context — and it reads that context through permission-aware access.

The workflow can only see what the user running it is allowed to see — grounding does not widen access.

The point of the studio layer is that business users can shape agent behaviour without going around the controls engineering relies on.

Studio Workflow vs Engineering Agent

The boundary is deliberate — knowing which side of it a task sits on is the skill.

Studio workflow (Module 09)

  • Authored by program / product / non-code users
  • Orchestrates a business process — reporting, triage, coordination
  • Runs in Rovo Studio, grounded on Jira & Confluence
  • Hands implementation to technical owners

Engineering agent (Modules 02–08)

  • Driven by engineers via Copilot / MCP
  • Makes the code changes — endpoints, tests, PRs
  • Runs in the IDE, CLI, or as the coding agent on the repo
  • Governed by repo instructions, MCP permissions, PR review

Three Workflow Use Cases

The hands-on picks one of these. Each has a natural trigger, a set of actions, and a point where a human must approve.

Trigger: a weekly schedule. Actions: read epics and issue status from the Jira project, pull release notes from Confluence, draft a program status summary. Approval: the program lead reviews and edits the summary before it is published.

Trigger: a new issue is created. Actions: classify it, suggest a component and priority, link likely-related issues. Approval: a triage owner confirms or overrides before the labels are applied.

Trigger: a release branch is cut. Actions: collect open blockers, cross-check the Confluence release checklist, draft the go/no-go note. Approval: the release manager signs off; technical owners implement any gating automation.
